# God Power — Design & As-Built Documentation

> **📌 Статус:** ✅ **ФИЧА ЗАВЕРШЕНА** (прототип + стартовая балансировка, влита в main)  
> **🏷️ Ветка:** `phase2/god-power`  
> **🎯 Результат:** Игрок-бог карает демонов: тап = AOE-молния, убийства заполняют круглый бар, при полном заряде — режим супер силы с массовым поражением и отменой

---

## 📚 1. Терминология и обзор механики

| Термин | Описание |
|--------|----------|
| **Молния (обычная атака)** | Тап по полю боя → белая вспышка, уничтожает до `lightningKillCount` ближайших монстров в радиусе `lightningRadius` |
| **Заряд** | Счётчик убийств молниями; каждое убийство заполняет круглый бар **снизу вверх** ярко-розовым (маджента). Сбрасывается между уровнями |
| **Иконка силы бога** | Круглая иконка с прогресс-баром в центральном слоте ряда стихий (заменила визуал «БАЗА», ГДД 2.4) |
| **Режим супер силы (armed)** | Активируется тапом по иконке при полном заряде; следующий тап по полю наносит супер удар |
| **Супер атака** | AOE: погибают **все** монстры в радиусе `superRadius`; бар сбрасывается в 0 |
| **Отмена** | Повторный тап по иконке в режиме armed возвращает обычные молнии |

Параметры баланса (ГДД 2.5, все конфигурируемые):

| Параметр | Дефолт | Где регулируется | Прокачка (будущее) |
|----------|--------|------------------|--------------------|
| `lightningKillCount` | 2 | Поп-ап, 1–100 | Да |
| `lightningRadius` | 60 css-px | Код (конфиг) | — |
| `superRadius` | 100 css-px | Поп-ап, 40–400 | Да |
| `superChargeRequired` | 40 | Код (конфиг; из поп-апа убран — разгрузка UI) | Нет (баланс) |

> Радиусы хранятся в css-px дизайна и умножаются на `UI_SCALE` при использовании — общий принцип масштабирования проекта.

## ❓ 2. История решений (Q&A)

1. **Тап по полю боя** — раньше спавнил 3 врагов (дебаг). → ⚠️ **Заменён на молнию**: с началом core геймплея тап — это атака. Спавн остаётся управляемым через поп-ап (интервал/лимиты).
2. **Радиус обычной молнии** — в таблице ГДД его нет (только `lightningKillCount`). → Добавлен `lightningRadius` в `GameConfig.godPower`: AOE без радиуса не определить.
3. **Кого убивает молния при переполнении зоны** → ближайшие к точке тапа (сортировка по d², срез лимита) — предсказуемо для игрока.
4. **Визуал «БАЗА»** → ⚠️ **Убран**: иконка силы бога встала ровно на её место (ГДД 2.4 «иконка базы заменена»). Логическая точка базы сохранена (невидимый rect 1×1) — монстры и физика используют её координаты как раньше.
5. **Килл монстра** = снятие с физики воркера (`removeAgent` + освобождение id) + возврат спрайта в пул (`killAndHide`) — никаких `destroy()`, ноль нагрузки на GC.
6. **Тапы по поп-апу настроек** → игнорируются полем боя (`settingsOpen` guard), иначе настройка параметров била молниями по толпе под поп-апом.
7. **arm() при неполном заряде** → тихо игнорируется (`false`), иконка не реагирует.
8. **Звуки** → нет, по ГДД («Прототип: Без звуков»).
9. **Супер атака по пустой зоне** → бар всё равно списывается: режим потребляется любым тапом по полю (по ГДД «следующий тап по полю боя → срабатывание»).
10. **Молния по пустой зоне** → вспышка без заряда: визуальный фидбек есть, наказания нет.

| Параметры конфигурируемые | ✅ Поп-ап настроек: 3 строки с [-]/[+] |

## 🔌 5. API

### GodPowerSystem (чистый TS, тестируемый без Phaser)

```ts
const gp = new GodPowerSystem(GameConfig.godPower);

gp.progress            // 0..1 заполнение бара
gp.isCharged           // заряд полон
gp.isArmed             // режим супер силы включён
gp.registerKills(n);   // учёт убийств молнией; true — бар заполнился только что
gp.arm();              // true — режим включён (требуется isCharged)
gp.disarm();           // отмена режима
gp.consume();          // number|null: радиус супер атаки + сброс бара/режима
gp.onBalanceChanged(); // клэмп после изменения superChargeRequired в настройках
```

Инварианты: `registerKills` не переполняет бар (cap на `superChargeRequired`); `consume()` без armed возвращает `null` и ничего не трогает; снижение `superChargeRequired` ниже текущего armed-заряда снимает режим.

### GodPowerIcon

```ts
new GodPowerIcon(scene, x, y, radius, system, onToggle: () => void);
icon.redraw();   // после каждого изменения заряда/режима (событийно, не каждый кадр)
icon.destroy();
```

Визуальные состояния (все части на уровне сцены в одной точке, БЕЗ контейнера — см. 6.7):
- **пустой/частичный**: чёрный круг, бледная молния (alpha 0.28), приглушённая обводка `0x7a2f7a`; маджента `0xff00ff` наливается **снизу вверх** (чёрный остаётся сверху);
- **полный заряд**: заметная пульсация (альфа залива 1↔0.55 + масштаб 1↔1.05, 650 мс) + вспышки-кольца, расходящиеся за пределы бара (~1 раз в 1.2 с);
- **armed**: все части масштабированы до 1.22 (микропульс 1.22↔1.3, 340 мс), молния белая, кольцо белое с сильным пульсом, яркое свечение — толстые кольца `BlendModes.ADD` вокруг кнопки (1.2R/1.5R/1.85R), вспышки-кольца чаще (850 мс).

Зона тапа — 3.2R вокруг центра (палец не промахивается). Твины расширения (вспышки/эффекты) используют `scaleX/scaleY`, а не tween `radius`: сеттер `Arc.radius` после `destroy()` обращается к занулённой геометрии и роняет кадр (Phaser 3.55).

## ⚙️ 6. Детали реализации (as-built)

### 6.1. Заливка бара снизу вверх (сегмент круга)

Бар — пересечение круга с полуплоскостью НИЖЕ уровня заряда (как жидкость в стаке: чёрный остаётся сверху, маджента наливается снизу). Уровень при прогрессе `p`: `dy = r − 2·p·r` (от центра, y-вниз: `+r` — пусто, `−r` — полон). Путь заливки:

```
хорда: (−w, dy) → (+w, dy),        w = √(r²−dy²)
дуга:  arc(0, 0, r, a, π−a),       a = atan2(dy, w)
```

Дуга идёт **через низ круга** (угол π/2), замыкание по хорде. Проверено краями и скриншотами: `p=0.25/0.6/0.85` — нижний сегмент растёт вверх, `p≥1` — `fillCircle` целиком.

> ⚠️ **История:** первая версия заливала область НАД уровнем — бар «резко становился маджентовым и заполнялся чёрным». Направление сегмента перепутали; починено по фидбеку плейтеста.

### 6.2. Выбор целей

`captureTargets(x, y, radiusPx, limit)`: один проход по детям пула врагов (только `active`), фильтр `d² ≤ r²`, сортировка по `d²` по возрастанию, срез до `limit` (`Infinity` для супер). Вызывается только по тапу — O(n log n) на событии, не в кадре.

### 6.3. Килл-логика (паритет воркер/fallback)

```
killEnemy(enemy):
  aid ≥ 0 и режим воркера → fluidCtrl.removeAgent(aid) + spriteById.delete(aid)
  enemies.killAndHide(enemy)   // возврат в пул
  enemyCount--
```

Id агента освобождается в контроллере и переиспользуется спавном; гонок с кадровым буфером нет: `handleFluidFrame` ищет спрайт по id и молча пропускает удалённых.

### 6.4. Ввод

Сцена: `pointerdown` → guard `settingsOpen` → guard `battlefieldZone` → `armed ? castSuperAttack : castLightning`. Иконка тапается независимо (зона в базе, вне поля боя). Тап по стихиям-алтарям не влияет на механику.

### 6.5. Вспышки

`createWhiteFlash(x, y, radiusPx, isSuper)`: ядро (0.35R / 0.45R) с `Quad.easeOut` 240/320 мс + кольцо-обводка с `Cubic.easeOut` 340/460 мс, `depth 900` (над монстрами, под дебаг-панелью 1000 и поп-апом 1200).

### 6.6. Интеграция со сценой

- Иконка создаётся в `createElements()` в центральном слоте ряда (радиус `baseElementSize * 0.62`), пересоздаётся при resize.
- `createBase()` оставляет только логическую точку (невидимый rect) — координаты базы для физики/движения не изменились.
- Поп-ап: 2 строки баланса (`lightningKillCount`, `superRadius`); `superChargeRequired` убран из поп-апа как перегруз UI — меняется в `GameConfig.godPower`. Высота панели: 10 строк.
- Дебаг-хук `window.__di = scene` (только при `GameConfig.game.debug`) — для headless-смоуков.
- `shutdown`: `godIcon = null`; твины и объекты чистятся сценой автоматически.

### 6.7. Грабли Phaser 3.55 (as-built, 23.08.2026)

1. **Кастомные пути Graphics внутри Container не рендерятся в WebGL** (`beginPath/moveTo/arc/fillPath` — тишина; при этом `fillCircle` и Arc-шейпы работают). Иконка поэтому собрана БЕЗ контейнера — все части на уровне сцены в одной точке, масштаб armed — твином `scale` по массиву частей.
2. **У Graphics origin (0,0)** — контент рисуется в локальных координатах вокруг (0,0), а сам Graphics позиционируется в центр иконки. Иначе `setScale` (armed-пульс) разъезжает залив от кнопки: при масштабе 1.22 контент на (225, 893) улетает на ~(50, 197) px.
3. **Аддитивные диски свечения выбеливают бар** (ADD-бленд поверх залива) — свечение делается толстыми кольцами ЗА пределами бара; вспышки armed — тоже кольца снаружи, а не диски.
4. **Tween `radius` на Arc + `destroy()`** — сеттер `radius` обращается к занулённой геометрии → «Cannot set properties of null». Все расширяющиеся эффекты — через `scaleX/scaleY`.

## ✅ 7. Верификация (headless Chrome, puppeteer)

Смоук против `vite preview`: загрузка → серия молний по толпе → тапы иконки → супер удар → повторный цикл. Состояние снимается через `window.__di`.

| Шаг | Результат |
|-----|-----------|
| 15 молний по толпе | 168 → 131 монстров, `progress: 0 → 1`, `charged: true` |
| Тап по иконке при заряде | `armed: true`, кольцо белое (скриншот) |
| Супер удар в гущу | 136 → 70 монстров, `progress: 0`, `armed: false` |
| arm без полного заряда (0.725) | заблокирован, `armed: false` |
| Повторный тап по иконке в armed | отмена, молнии работают |
| Ошибки консоли/pageerror | нет |
| `tsc --noEmit` + `vite build` | чисто |

Финальная визуальная верификация (скриншоты headless Chrome, 23.08.2026): частичные заливы `p=0.25/0.6/0.85` — маджента снизу, чёрный сверху; полный — пульс альфы и масштаба в серии кадров; armed — кнопка увеличена, белое кольцо, свечение-кольца вокруг, вспышки. HP базы сохраняется между уровнями, заряд сбрасывается при смене уровня.

### Этап 2: Балансировка — ✅ стартовая (23.08.2026)
- Дефолты выставлены: 2 убийства/молния, радиус супера 100 (при заряде 40).
- Визуал бара финализирован по плейтесту: маджента снизу вверх, пульс+вспышки на полном, armed-свечение (см. 6.7).
- Финальный тюнинг — по плейтестам на мобильных; тогда же решить: нужен ли `lightningRadius` в поп-апе (сейчас только в коде).
- A/B на мобильных: размер зоны тапа иконки (3.2R), длительности вспышек.

### Этап 3: Прокачка в геймплее — ⏳ (ГДД: «прокачивается»)
- Источник прогресса: за волну/уровень/серию убийств — **требуется решение**.
- Рост `lightningKillCount` и `superRadius` по уровням; `superChargeRequired` фикс.
- Сохранение прокачки через SaveSystem (фаза полировки).

### Этап 4: Полировка — ⏳
- Визуал молнии: луч с неба/зигзаг вместо точки вспышки, частицы на жертвах.
- Тряска камеры на супер атаке.
- Звуки (снято ограничение «прототип без звуков»).

### Этап 5: Интеграция со стихиями — ⏳ (Фаза 2, п.3–4 ГДД)
- Разведение жестов: тап = молния, слайд = рисование стихии.
- Приоритет/комбинации: супер в зоне стихии и т.п. — определить при проектировании ElementSystem.

## ⚠️ 9. Риски и открытые вопросы

1. **Жест-конфликт с рисованием стихий** — тап уже занят молнией; при появлении слайд-жеста нужно чёткое разделение (порог перемещения указателя).
2. **Супер по пустому месту сжигает заряд** — осознанно (по ГДД), но на мобильных случайные тапы у кромки могут раздражать; кандидат на пересмотр после плейтеста.
3. **Прокачка без определённого источника очков** — блокер для этапа 3, не для текущего прототипа.
4. **`lightningRadius` не в настройках** — при балансировке может понадобиться вынести в поп-ап.
