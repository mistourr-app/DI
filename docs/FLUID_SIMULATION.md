# Fluid Simulation — Design Document

> **📌 Статус:** 📋 Планирование (документ утверждается)  
> **🏷️ Ветка:** `phase2/fluid-simulation`  
> **🎯 Цель:** Перенести физику толпы в Web Worker и сделать поведение монстров «как жидкость»: обтекание препятствий реками, расталкивание в толпе — при 1000+ агентов на экране без просадок FPS

---

## 📚 1. Цель и требования

### Источник требований
[GDD §2.1](../GAME_DESIGN_DOCUMENT.md): **до 1000 врагов на экране**, поведение моделируется как жидкость, визуализация — маленькие спрайты, объединённые в «поток». Техстек явно предписывает **Web Workers** для fluid simulation. Целевой FPS — 60.

### Что значит «жидкость» на практике
| Наблюдение | Механика |
|------------|----------|
| Толпа течёт вокруг препятствий «рукавами» | Steering к базе + коллизии со стенами (уже есть) + расталкивание соседями |
| Монстры не слипаются в одну точку | Сила separation по spatial hash |
| Плотная толпа «распирает» изнутри | Pressure от локальной плотности |
| Поток движется согласованно, без дёрганья | Viscosity / alignment к средней скорости соседей |
| Рукава держатся вместе, но не сливаются | Слабая cohesion |

## 🔍 2. Текущее состояние

### Что заменяется
Движение сейчас целиком на main thread (`GameScene.updateEnemyMovement`):
- пул Image-спрайтов `'enemy'`, скорость в прямых свойствах `vx/vy`;
- steering к базе + шум ±0.01, клэмп `maxSpeed×1.05`;
- осевое скольжение по сетке `LevelGenerator.isBlocked` (CELL=16px), радиус-хитбокс `isBlockedBox` (4 угла, `hitR = max(4, enemySize·0.6)`);
- спасение застрявших (nudge вверх), боковые клэмпы поля;
- достижение зоны базы → `killAndHide()` → HP−1;
- спавн: раунд-робин по полноширинному входу над экраном (`zone.y − 32`).

При 1000+ агентов это уже работает в 60 FPS, но толпа ведёт себя как «рой независимых точек», а не жидкость, и вся физика лежит на главном потоке.

### Что переиспользуется как есть
| Актив | Как используется во fluid sim |
|-------|-------------------------------|
| Сетка коллизий `level.isBlocked` (Uint8Array 16px) | Копия передаётся в воркер; та же семантика осевого скольжения |
| Пул спрайтов `'enemy'` + Group | Рендер остаётся на main; позиции приходят из воркера |
| Спавн/деспавн, счётчики, HP базы, поп-ап ⚙ | Остаются на main; физике шлются только события add/remove |
| `GameConfig.enemies.fluid` | Константы сил уже заготовлены: `density 1.0, pressure 0.1, viscosity 0.01, separation 1.5, cohesion 0.5, alignment 0.3` — будут подключены |

### Что удаляется
- `src/game/utils/WorkerPool.ts` — task-based promise-pool: избыточен для непрерывной симуляции, `postMessage` без transfer list, сломанный выбор воркера (+ висящая TS-ошибка). Заменяется специализированным контроллером (§6).

### Вне рамок фичи
- ECS (`World.ts`, `CrowdAgent.ts`) — в рантайме движения не участвует; миграция агентов в bitecs — отдельное будущее решение.
- Рисование стихий, комбинации элементов — следующие задачи Фазы 2.

## 🏗 3. Архитектура

### 3.1. Ключевые решения

| # | Решение | Обоснование |
|---|---------|-------------|
| 1 | **Один выделенный worker** (не пул) | Симуляция непрерывна: состояние живёт в воркере постоянно. Пул нужен для разовых задач, не для 60 шагов/сек |
| 2 | **SoA-память**: `Float32Array px/py/vx/vy/radius`, ёмкость `MAX_AGENTS = 4096`; занятость через free-list (`Int32Array` стек) + `count` | Кэш-дружественно, ноль аллокаций в цикле, O(1) add/remove |
| 3 | **Transferable ping-pong буферов**, без SharedArrayBuffer | SAB требует COOP/COEP заголовков (усложняет dev/PWA/хостинг); копия 1000 агентов = ~16 KB/кадр — бесплатно |
| 4 | **Stepping управляет main**: каждый rAF шлёт `{type:'step', dt}` пока предыдущий кадр in-flight | Сим синхронна с рендером; внутри воркера фиксированный подшаг `1/60` c аккумулятором (макс. 3 подшага за кадр) |
| 5 | **Силы — SPH-lite/boids гибрид** поверх steering'а к базе | Дешевле полного SPH, даёт нужный «жидкий» вид; константы уже в конфиге |
| 6 | **Сетка коллизий копируется в воркер** при init и при каждой регенерации уровня | Коллизии считаются там же, где интеграция; main освобождён полностью |
| 7 | **Спавн/килл остаются на main** | Пул спрайтов, счётчики, HP — UI-состояние; воркеру шлются только `{add}/{remove}` |
| 8 | **Fallback main-thread** при отсутствии Worker | Игра остаётся играбельной везде; текущий код движения сохраняется как legacy-путь |

### 3.2. Поток данных за кадр

```
main thread                              FluidWorker
───────────                              ───────────
rAF:
  spawn?  ──{add id,x,y,vx,vy}──────────► free-list push
  kill?   ──{remove id}─────────────────► free-list pop
  если нет in-flight:
    ──{step, dt} + свободный out-буфер─►  fixed substeps ×N:
                                          1. rebuild spatial hash
                                          2. forces (steer+sep+press+visc)
                                          3. integrate (substep dt)
                                          4. collide (grid slide)
                                          5. collect arrived ids
    ◄─{frame, px,py[transfer], arrived}─
  sync sprites ← px/py (Map id→sprite)
  arrived → killAndHide, HP−−
```

### 3.3. Протокол сообщений

| Направление | type | Payload | Transfer |
|-------------|------|---------|----------|
| main→w | `init` | width, height, maxAgents, params(fluid) | — |
| main→w | `set_level` | cols, rows, cellSize, blocked(Uint8Array) | blocked ✅ |
| main→w | `add` | id, x, y, vx, vy, radius | — |
| main→w | `remove` | id | — |
| main→w | `step` | dt | out-буфер позиций ✅ |
| main→w | `params` | targetSpeed, enemyRadius, … | — |
| w→main | `ready` | — | — |
| w→main | `frame` | count, px(Float32Array), py(Float32Array), arrived(Int32Array) | все три ✅ |

Буферы позиций возвращаются main'ом воркеру вместе со следующим `step` (пул ≥2 буферов на стороне main).

### 3.4. Spatial hash
- Ячейка ≈ радиус взаимодействия (~24px), отдельная от коллизионной сетки 16px.
- Реализация linked-cell без аллокаций: `Int32Array head[hash]` + `Int32Array next[MAX_AGENTS]`.
- Поиск пар — только по своей ячейке + 8 соседних.

## ⚙️ 4. Алгоритм сил (на подшаг)

```
для каждого агента i:
  n      = соседи в радиусе R_sep (hash)
  dens_i = |n|
  
  steer  = normalize(base − p_i) · targetSpeed          // как сейчас
  sep    = Σ_neighbors (p_i − p_j)/d²  · k_sep          // сильнейший вклад
  press  = dens_i > D_max ? (centroid_n − p_i)·k_press : 0
  visc   = (avg(v_n) − v_i) · k_visc                    // сглаживание потока
  coh    = (centroid_n − p_i) · k_coh                   // слабая

  a      = steer·w_steer + sep·k_separation + press·k_pressure 
           + visc·k_viscosity + coh·k_cohesion
  v_i   += a · substepDt
  clamp |v_i| ≤ maxSpeed·1.05
  p_i   += v_i · substepDt
```

Константы `k_*` стартуют из `GameConfig.enemies.fluid`; тюнинг — Фаза 2. Steering остаётся базой движения (монстры обязаны доходить до базы), силы жидкости модулируют траекторию, а не заменяют цель.

## 🧱 5. Коллизии и границы (в воркере)

- Семантика идентична текущей main-реализации: осевое скольжение `(nx,ny)` → `(nx,y)` → `(x,ny)` → стоп.
- Хитбокс: центр + 2 пробы вдоль вектора скорости (`±radius·0.6`). При визуальных артефактах поднимается до 4 углов как на main.
- Боковые границы поля: клэмп + демпфирование нормальной составляющей (как сейчас).
- Верхняя граница: клэмпов нет — агенты заходят сверху свободно (фикс застревания учтён).
- **Достижение базы:** `y > battlefieldHeight` → id уходит в `arrived[]` → main делает `killAndHide` и снимает HP. Логика базы полностью на main.

## 📁 6. Интеграция и файлы

```
src/game/
├── fluid/                            # НОВОЕ
│   ├── fluidProtocol.ts              # Типы сообщений, константы, чистые функции сил
│   │                                 # (импортируются ОБЕИМИ сторонами — единая физика)
│   ├── FluidWorker.ts                # Воркер: substeps, hash, силы, коллизии
│   └── FluidSimulationController.ts  # Main-side: lifecycle, ping-pong, API для сцены
├── utils/
│   └── WorkerPool.ts                 # УДАЛИТЬ
└── generation/
    └── LevelGenerator.ts             # + маленькое API: getCollisionField() →
                                      #   {cols, rows, cellSize, blocked} (копия сетки;
                                      #   сама сетка иммутабельна после генерации)
scenes/GameScene.ts                   # Контроллер вместо updateEnemyMovement;
                                      # render-sync спрайтов; хуки spawn/kill
```

- Создание воркера: `new Worker(new URL('./FluidWorker.ts', import.meta.url), { type:'module' })` (нативная поддержка Vite 5).
- **Fallback:** `typeof Worker === 'undefined'` → `controller.isWorkerMode=false` → работает текущий `updateEnemyMovement`. Чистые функции сил импортируются обоими путями — расхождение физики исключено.
- Поп-ап ⚙: параметры спавна форвардятся в воркер (`params`); слайдеры сил — Фаза 3.

## ✅ 8. Критерии приёмки фичи

- [ ] 1000+ монстров @ 60 FPS (desktop Chrome); средний мобильный ≥ 30 FPS
- [ ] Main thread не считает физику: только синхронизация позиций спрайтов (<1 мс/кадр)
- [ ] Шаг воркера ≤ 8 мс на 1000 агентов (без аллокаций в steady-state)
- [ ] Толпа обтекает блобы «реками»; в плотных местах — расталкивание; нет взаимных наложений
- [ ] Лабиринт непроходим (семантика сетки сохранена 1-в-1)
- [ ] Достижение базы убивает агента и снимает HP (через arrived-list)
- [ ] Регенерация уровня / кнопка «Сгенерировать уровень» корректно обновляют воркер
- [ ] Режим без Worker (fallback) играбелен

## ⚠️ 9. Риски и решения

| Риск | Решение |
|------|---------|
| Задержка позиций на 1 кадр | Приемлема визуально; при необходимости — интерполяция позже |
| GC pressure от постинга буферов | Transferables + переиспользуемый пул буферов; ноль аллокаций в воркере |
| Дублирование физики (worker vs fallback) | Единый модуль чистых функций, импортируется обеими сторонами |
| Бандлинг worker + vite-plugin-pwa | Проверяется первой же задачей Фазы 1 (1.6), до углубления |
| Расхождение хитбоксов (main 4 угла vs worker пробы) | Стартуем с проб; артефакты → поднимаем до 4 углов |
| «Вязкая» толпа перекрывает проход < passageWidth | Pressure-порог D_max настраивается; passageWidth уже гарантирует мин. просвет генератором |
