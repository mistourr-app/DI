# Level Generation — Design & As-Built Documentation

> **📌 Статус:** ✅ **ЗАВЕРШЕНО** (Фаза 1 MVP + Фаза 2 + оптимизации)  
> **🏷️ Ветка:** `phase2/level-generation`  
> **🎯 Результат:** Детерминированная генерация уровней по seed с органическим лабиринтом, гарантией 100% проходимости и коллизиями, не влияющими на FPS

---

## 📚 1. Терминология

### Области экрана
| Область | Описание | Пропорция |
|---------|----------|-----------|
| **Игровое поле** | Общая область игры (соотношение 9:19.5), центрируется | 100% |
| **Поле боя** | Область лабиринта и монстров | 5/6 высоты игрового поля |
| **Зона базы** | Нижняя область с базой и элементами | 1/6 высоты игрового поля |

### Компоненты уровня (как реализовано)
| Компонент | Расположение | Назначение |
|-----------|-------------|------------|
| **Вход** | Вся верхняя граница поля боя (единый, ширина = ширине поля) | Монстры спавнятся над экраном по всей ширине |
| **Выход** | Вся нижняя граница поля боя (единый, ширина = ширине поля) | Свободная зона выливания потоков к базе |
| **Лабиринт** | От верхней кромки до начала нижней свободной полосы | Органические блобы из simplex-шума, без отступов от краёв |
| **Движение монстров** | Сверху вниз: спавн → лабиринт → база; разбивку на потоки делает сам лабиринт | Пока простое движение к базе + скольжение по стенам; fluid simulation — отдельный будущий модуль |
| **Проходимость** | ✅ **100%**, гарантирована BFS-проверкой с прорезкой коридоров | См. §6 |

> ⚠️ **Отступление от исходной концепции:** изначально предполагались 1–5 дискретных входов/выходов. В ходе реализации принято решение сделать **один вход и один выход на всю ширину поля**: толпа заходит единым потоком и делится на рукава прорехами в верхнем ряду блобов. Это визуально честнее — то, что выглядит как проход, и есть путь.

## ❓ 2. История решений (Q&A)

> Исходные ответы пользователя сохранены для истории. Решения, пересмотренные в процессе реализации, помечены ⚠️.

1. **Сколько входов?** ~~Случайно 1–5, ширина от 1/10 до 100%~~ → ⚠️ **Один вход на всю ширину поля**
2. **Сколько выходов?** ~~Случайно 1–5~~ → ⚠️ **Один выход на всю ширину поля** (нижняя полоса ~1/10 высоты свободна от препятствий)
3. **Распределение входов/выходов** → ⚠️ Неактуально при полноширинных входе/выходе
4. **Форма препятствий** → ✅ Любые формы; реализованы как **органические блобы** (шум → контурная трассировка → сглаживание Chaikin)
5. **Настраиваемые параметры** → ✅ `obstacleDensity` (0–1), `passageWidth` (мин. проход, px); параметры передаются в `LevelGenerator.generate()`
6. **Обход препятствий монстрами** → Промежуточно: движение к базе + осевое скольжение вдоль стен (fluid simulation остаётся отдельной задачей)
7. **100% проходимость** → ✅ Гарантирована алгоритмом (см. §6)
8. **Выбор пути** → fluid simulation (отдельный модуль, вне рамок этой фичи)
9. **Отображение лабиринта** → ✅ Контур + сплошная заливка (`fillPoints` + `strokePoints`, заливка `#39445C`, контур `#AEBFDD`)
10. **Отображение входов/выходов** → ✅ Нет (временные debug-маркеры использовались и удалены)
11. **Максимальное число препятствий** → Определяется плотностью; ограничений сверху не вводилось
12. **Оптимизация генерации** → Генерация <50 мс, выполняется разово при создании/resizе; Web Workers не требуются

## 🎯 3. Технические требования — статус

| Требование | Статус |
|------------|--------|
| Один `seed` → идентичный уровень | ✅ Seeded RNG (xmur3+mulberry32), Math.random в генераторе отсутствует |
| Адаптация под размеры экрана | ✅ Перегенерация при resize с тем же seed (`handleResize`) |
| Генерация не блокирует UI | ✅ <50 мс на типичных размерах поля, разовый вызов |
| Интеграция с GameScene | ✅ `generateLevel()` / `renderObstacles()` |
| Непроходимость препятствий | ✅ Сеточные коллизии O(1) со скольжением |
| Seed через SaveSystem | ⏳ Вне рамок этой фичи (фаза полировки GDD); сейчас seed живёт в рамках сессии страницы |

## 🔧 5. API генератора

```typescript
import { LevelGenerator } from './game/generation/LevelGenerator';

const generator = new LevelGenerator();

const level = generator.generate({
  seed: 'seed-lxk29f',        // строка любой длины
  width: battlefield.width,   // локальная система координат поля боя
  height: battlefield.height, // (0..width, 0..height), оффсет добавляет сцена
  passageWidth: 60,           // мин. ширина прорезаемых коридоров, px (опц., 60)
  obstacleDensity: 0.4        // 0..1, порог шума (опц., 0.4)
});

// O(1)-коллизия. Координаты ЛОКАЛЬНЫЕ; вне поля → false.
level.isBlocked(localX, localY);

// Данные для рендера: замкнутые сглаженные полигоны
level.obstacles.forEach(poly => drawPoints(poly.points));

// Совместимость с прежним API: один полноширинный вход/выход
level.entrances; // [{ x: width/2, y: 0,      width }]
level.exits;     // [{ x: width/2, y: height,  width }]
level.seed; level.width; level.height;
level.basePosition; // { x: width/2, y: height }
level.spawnPoints;  // центры входов (сцена использует entrances напрямую)
```

## 🧩 6. Алгоритм генерации (as-built)

Все шаги детерминированы: единственный источник случайности — `mulberry32(xmur3(seed)())`; `SimplexNoise` строится на этом же ГПСЧ.

### 6.1. Сетка коллизий
- Клетка **16×16 px** (`CELL`), поле `ceil(width/16) × ceil(height/16)`, `Uint8Array`.
- Сетка хранится внутри замыкания `isBlocked()` — наружу не отдаётся, изменению после генерации не подлежит.

### 6.2. Блобы препятствий (органические формы)
- Две октавы simplex-шума:
  `u = (noise2D(x·0.006, y·0.006)·0.72 + noise2D(x·0.02+cst, y·0.02+cst)·0.28 + 1) / 2`
- Порог: `threshold = 0.685 − density·0.25` (density=0.4 ≈ 30% заполнения).
- Клетка занята, если `u > threshold`.
- **Свободные зоны:** только нижняя полоса `height × 0.1` (клэмп [2·CELL … 25% высоты]). Верхняя кромка и бока — **без отступов**: блобы начинаются прямо от краёв поля.

### 6.3. Гарантия 100% проходимости
1. **Страховка входа:** если шум закрыл весь ряд 0 сплошняком, освобождаются центральные клетки ряда (иначе уровень непроходим в принципе).
2. **BFS:** многоисточниковый поиск от всех свободных клеток **ряда 0** — всё, что входит в поле, обязано пройти через них (бока поля — стены).
3. **Проверка выхода:** достигнута ли нижняя свободная полоса.
4. **Прорезка:** если нет — от ближайшей достигнутой клетки к точке `(width/2, height − bottomMargin/2)` прокладывается коридор «кистью» радиуса `max(passageWidth/2, CELL·1.25)`; затем BFS повторяется. Максимум 25 итераций.

### 6.3.5. Заливка недренируемых карманов (as-built, 22.08.2026)
BFS из 6.3 пускается в **4 направления** и не учитывает семантику движения монстров
(строго вниз + скольжение вбок). Глубокие выемки (U-образные карманы) и замкнутые
полости остаются «проходимыми» по BFS, но монстры не могут их покинуть.

- **Модель дренируемости:** клетка безопасна ⇔ существует путь `{вниз, влево, вправо}`
  до нижней свободной полосы. Расчёт снизу вверх: прямое падение + горизонтальное
  замыкание строки двумя проходами LR/RL.
- **Заливка:** все свободные небезопасные клетки → `blocked=1`. Полигоны строятся
  после заливки — ландшафт бесшовный, детерминизм сохранён (чистая функция сетки).
- **`ensureTopEntrances` (страховка входа):** если заливка запечатала весь ряд 0,
  пробиваются вертикальные дренажные шахты от кромки до нижней полосы (~каждые
  240px), затем заливка повторяется. Шахта — цепочка свободных клеток друг под
  другом, поэтому дренируема по построению.
- **Валидация:** headless-прогон 20 seed'ов × 300 точечных агентов через реальную
  `moveDownStep`: **300/300 доходят на каждом seed'е**, недренируемых клеток 0.
  Гарантия для агентов с радиусом держится на `passageWidth ≥ 60px`.

### 6.3.6. Ширина проходов и лимит кластеров (as-built, 22.08.2026)
Шум сам по себе даёт слишком узкие щели и гигантские сросшиеся кластеры.

- **`sealThinPassages`** — эрозия свободного места ядром 3×3: клетка выживает только
  со всеми свободными соседями ⇒ минимальный проход **3 клетки = 48px**. Вне-сеточные
  клетки считаются свободными (кромки не запечатываются). Выполняется сразу после шума.
- **`splitOversizedClusters`** — связные компоненты препятствий (4-связность, BFS):
  если крупнейшая занимает > `MAX_CLUSTER_RATIO = 0.12` площади поля — режется крестом
  коридоров («кисть» радиуса `max(passageWidth/2, CELL·1.25)`) через центр bbox,
  до 8 итераций.
- Порядок пайплайна: шум → герметизация → резка кластеров → проходимость (6.3) →
  заливка карманов → страховка входов.
- Эффект: поток доходит до базы в ~1.5–2× быстрее (меньше детур-ов), перф вырос
  (~0.59 мс/шаг @1000 агентов — меньше соседей в радиусе).

### 6.4. Контуры → полигоны (для рендера)
- По каждой занятой клетке выпускаются направленные граничные рёбра (по часовой стрелке, внутренность слева).
- Рёбра сцепляются по совпадающим концам в замкнутые петли (диагональные касания дают корректное ветвление — каждая грань используется ровно один раз).
- Петли сглаживаются **Chaikin ×2** → плавные органичные силуэты без угловатости клеток.
- Мусор отбрасывается по площади (формула шнурования): петли < `2·CELL²` удаляются.
- Незамкнутые цепи пропускаются (не возникают на валидной маске, но проверяются).

### 6.5. Рендер (GameScene)
- Один `Phaser.GameObjects.Graphics`, рисуется **один раз** на уровень (`renderObstacles()`), не в кадровом цикле.
- Каждый полигон: `fillStyle(0x39445c).fillPoints(pts, true)` + `lineStyle(2, 0xaebfdd, 0.9).strokePoints(pts, true)` — контур + сплошная заливка по доке.
- При перегенерации старый Graphics уничтожается.

## 🎮 7. Интеграция со сценой

### Жизненный цикл уровня
- `create()` → `new LevelGenerator()` + `generateLevel()`
- `scale.on('resize')` → `setupScreenZones()` + `generateLevel()` (**тот же seed** → тот же лабиринт под новый размер)
- Поп-ап «⚙ НАСТРОЙКИ» → кнопка **«Сгенерировать уровень»** → новый случайный seed → `scene.restart()`
- Очистка: `events.once('shutdown')` снимает resize-обработчик (иначе после рестарта он дублируется)

### Спавн монстров
- Таймер в `update()`: интервал (по умолчанию 30 мс), лимиты `maxEnemiesOnScreen` (1000) и волны (25K); максимум 1 спавн за кадр.
- X — равномерно по всей ширине поля (`round-robin` по единственному полноширинному entrance), Y — над экраном: `battlefieldZone.y − 32 ± 10`.
- **Пул объектов**: `getFirstDead()` / `killAndHide()` — ноль аллокаций в бою.

### Коллизии
- Осевое скольжение: пробуем `(nx,ny)`, иначе `(nx,y)`, иначе `(x,ny)`, иначе стоим.
- **Радиус-коллизия** `isBlockedBox()`: проверяются 4 угла квадрата вокруг центра, `hitR = max(4, enemySize·0.6)` — крупные монстры не «проваливаются» в блобы визуально.
- Точки выше кромки поля свободны (`isBlocked` вне сетки → false) — монстры корректно скользят вдоль свисающих сверху стен ещё до входа в поле.
- **Клэмп по верхней границе удалён**: раньше он телепортировал свежий спавн внутрь верхних блобов (застревание). Спасение: если центр оказался в блоке — монстр выползает вверх до свободной зоны.

## ⚡ 8. Производительность (замерялось A/B-тестом в headless Chrome)

| Оптимизация | Было | Стало |
|---|---|---|
| Рендер монстров | Arc-фигуры, ~1000 draw call'ов | Image-спрайты общей текстуры `'enemy'` → **один батч** |
| Скорость врага | `getData`/`setData` (Data Manager) ×2000/кадр | прямые свойства `vx/vy` |
| Дебаг-текст | `setText` каждый кадр | троттлинг 250 мс |
| Жизненный цикл | destroy/new (GC-прессинг) | пул |
| Циклы | `forEach` + замыкания | индексный `for` |

**Результат A/B (одинаковая headless-среда, rAF-замеры):** 7.1 FPS @ 356 монстров → **16.6 FPS @ 575 монстров** (потолок софтверного рендерера среды ~18 FPS; стоимость рендера монстров упала с ~10 до ~1.7 fps-бюджета). На GPU-браузере — стабильные 60 FPS.

## ✅ 9. Критерии приемки — выполнено

### MVP (Фаза 1)
- [x] Уровень генерируется по seed (детерминированно)
- [x] Вход и выход расположены на границах поля боя *(реализованы полноширинными — см. §1)*
- [x] Препятствия любых форм отображаются (контур со сплошной заливкой)
- [x] Монстры не проходят сквозь препятствия
- [x] Уровень адаптируется под размеры экрана

### Полная реализация (Фазы 1–2)
- [x] Органические формы препятствий (шум + трассировка + Chaikin)
- [x] 100% проходимость (BFS + прорезка коридоров ≥ passageWidth)
- [x] Настраиваемые параметры генерации (`obstacleDensity`, `passageWidth`); поп-ап «Сгенерировать уровень» с новым seed
- [ ] Seed сохраняется и загружается — **⏳ перенесено в фазу SaveSystem** (GDD, Фаза 3)

### Сверх плана
- [x] Оптимизация рендера толпы (спрайт-батчинг, пул, троттлинг текста) — A/B-верифицировано
- [x] Радиус-коллизии + защита от застревания у верхней кромки
